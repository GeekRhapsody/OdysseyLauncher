# Odyssey Launcher

A fully 3D game launcher frontend (systems grid → games grid → emulator), styled after the PS2 memory card browser. It's built with Godot 4.7 .NET and C#, for Windows first, Linux later if cheap, and never macOS. **Performance is the headline feature.**

- The design is in `docs/ARCHITECTURE.md`. Add to its decisions log whenever a decision changes: an entry is the decision and its why, in at most about 80 words, and the detail goes in the section it changes. A console card's build record (its construction, clip and fixes) goes in `tools/console-models/HISTORY.md` instead.
- Milestones and acceptance criteria are in `docs/ROADMAP.md`. Update its **Progress** section at the end of every milestone.
- `CHANGELOG.md` is the release notes. Add every change a user will notice (a feature, a changed default, a fix) under its `## Unreleased` section, in the same piece of work, most important first: plain words for users, no internal names. A release needs a section there (`release.ps1` names it after the version), and the release page and the app's "Check for updates" show it.
- The guide for theme authors is `docs/THEMING.md`. Keep it in step with the manifest, the slots, the model spec and the budgets.
- The GitHub wiki (`https://github.com/GeekRhapsody/OdysseyLauncher.wiki.git`, a separate git repo: clone it outside this one, edit, commit, push to `master`) has three articles that copy this repo's docs, so update them in the same piece of work as the change: `ROM-folder-names` (every built-in system's folder name and aliases, generated from `src/Launcher.Core/Defaults/systems.toml`: update it when a system, its id or an alias is added, renamed or removed), `Creating-themes` (a practical version of `docs/THEMING.md`: update it when the manifest, slot or clip names, the model spec, the budgets or publishing a theme change) and `Downloading-themes` (the settings' theme downloader, for users: update it when its page, `themes.json` or where it keeps its files change; docs/ARCHITECTURE.md A6, "Downloading themes"). Keep its `Home` page's list of articles current when you add one.

## Layout

| Path | What |
|---|---|
| `src/Launcher.Core/` | Plain .NET class library: config, DBs, scanning, scraping, launching, platform, diagnostics. **No Godot reference.** |
| `src/Launcher.Updater/` | `OdysseyUpdater.exe`, the update helper (docs/ARCHITECTURE.md A1 "Updates"): installs a downloaded update once the launcher has quit, then starts it again. No reference to Core. Every Windows export publishes it with Native AOT (`godot/addons/odyssey_export/UpdaterExportPlugin.cs`) beside the executable; that needs the Visual Studio C++ build tools. The tests run its plain build. |
| `tests/Launcher.Core.Tests/` | xUnit v3 tests for Core. |
| `tests/FakeEmulator/` | A console app the launch tests run as a stand-in emulator. It logs its arguments, sleeps, exits with a chosen code, and can act as a stub launcher (options in its `Program.cs`). |
| `godot/` | The Godot project. `OdysseyLauncher.csproj` references Core. C# scripts live in `godot/src/`, in namespace `Launcher.App`. |
| `src/Launcher.Core/Defaults/` | The built-in `settings.toml`, `systems.toml`, `emulators.windows.toml` and `emulators.linux.toml` (each OS its own, complete, a profile with the same emulator having the same id and name in both: docs/ARCHITECTURE.md A5, "Built-in emulators on Linux", 2026-11-03), and `settings.linux.toml` and `systems.linux.toml`, merged over the shared ones on Linux. Embedded in Core: the original 14 systems, then ES-DE's catalogue (docs/ARCHITECTURE.md A5, "The ES-DE catalogue"), with Windows, Steam and Desktop Apps ("Windows and Steam games"), and regional variants after the system each varies (A5, "Regional variants": `dreamcastnajp`, Dreamcast (NA/JP), 2026-11-02; `segacd`, Sega CD, and `megacdjp`, Mega-CD (JP), after `megacd`, Mega-CD, 2026-11-03, and `sfc`, Super Famicom, after `snes`, the European system being the one a variant varies; a variant's extensions, emulators and scraping ids are its system's, which `ConfigLoaderTests` checks; its `group` shows its games in its system's card, A5 "Grouped systems", 2026-11-03). Keep them plain TOML (tables, bare keys, strings, numbers, booleans, single-line arrays): `TomlFast` reads them and `TomlFastTests` checks it builds Tomlyn's tree. |
| `src/Launcher.Core/Data/Migrations/` | Numbered SQL migrations for `library.db` and `userdata.db`, embedded in Core. |
| `tools/verify.ps1` | Runs every non-windowed check. |
| `release.ps1` | Bumps the version, commits, tags and pushes a release (see Commands). Gitignored: the owner's own copy. |
| `CHANGELOG.md` | The release notes, a `## <version> (<date>)` section a release, newest first, under `## Unreleased` (what's done since the last release). |
| `tools/release-notes.ps1` | Prints a version's section of `CHANGELOG.md` (or writes it with `-Out`), failing when there's none or it's empty: `release.ps1` checks with it before tagging, and the release workflow puts it on the release. |
| `.github/workflows/release.yml` | The Windows and Linux release (docs/ARCHITECTURE.md decisions log, 2026-10-01 and 2026-11-05), on a pushed `v<version>` tag, in four jobs. `version` checks the tag against the version and that `CHANGELOG.md` has its notes, so a tag without notes stops before any build. `windows` writes the built-in ScreenScraper developer credentials from the repository's secrets (`tools/write-built-in-accounts.ps1`), builds, tests (not the benchmarks), exports Windows and Linux on the runner's software GPU (WARP; each export must have its themes, Windows a Native AOT `OdysseyUpdater.exe`), runs the launch smoke test on the Windows export and zips it. `linux` (ubuntu-24.04) makes the AppImage from the Linux export with `tools/linux/`'s `setup.sh` (FFmpeg's build cached by its recipe), `test.sh`, `make-appimage.sh` and `smoke.sh`, then runs it headless in an `almalinux:9` container (glibc 2.34). `release` attaches `OdysseyLauncher-<version>-windows-x86_64.zip`, `OdysseyLauncher-<version>-linux-x86_64.AppImage`, their `.sha256` files and the AppImage's `.zsync` to the tag's release, whose notes are the version's section of `CHANGELOG.md` and then GitHub's compare link. Run by hand (Actions > Release), it's a test build kept as the run's two artifacts. |
| `tools/launch-smoke.ps1` | Runs the app with `--launch` against the fake emulator, in an isolated user folder. |
| `tools/linux/` | The Linux AppImage (docs/ARCHITECTURE.md decisions log, 2026-11-02), made on Windows with a WSL distro of its own (`OdysseyLinux`, Ubuntu 24.04, used as root), and by the release workflow's `linux` job (as a user, with sudo for apt): `make-appimage.ps1` (the one command: the Linux export, then the rest in WSL), `setup.sh` (the pinned tools: .NET in `~/.dotnet`, PowerShell 7, appimagetool and the type2 runtime, by version and SHA-256 in `common.sh`; what's missing of Ubuntu's C tools, `zsync`, `appstream` and `fuse3` by apt, through sudo when not root; and FFmpeg for videos (L4), built from its pinned source tarball in about a minute and a half into `~/.cache/odyssey-linux/native/`, kept to glibc 2.34 by `glibc-floor.h`, with its struct offsets from `ffmpeg-abi.c`; and PDFium for manuals, pdfium-binaries' `libpdfium.so`, pinned by release and SHA-256), `test.sh` (the build and tests on Linux, from a copy of the tree in `~/.cache/odyssey-linux/repo`, so the checkout's Windows `bin/` and `obj/` stay as they are, with the native libraries copied beside the tests), `make-appimage.sh` (an export into `artifacts/linux/OdysseyLauncher-<version>-linux-x86_64.AppImage`, its `.sha256` and its `.zsync`: the native libraries in `usr/lib` and their licences in `usr/share/licenses`, every ELF file checked against glibc 2.34, AppRun, the desktop entry and AppStream metadata named by the app's id, `io.github.geekrhapsody.OdysseyLauncher.desktop` and `.appdata.xml` (in `usr/share/applications` and `usr/share/metainfo`, validated by appstreamcli; 2026-11-05), zsync's update information (`latest`, or `latest-all` for a pre-release), and `odyssey-launcher.png`, which `tools/app-icon/make_icon.py` writes), `make-test-videos.sh` (the committed test videos in `tests/Launcher.Core.Tests/Media/Videos/`, with Ubuntu's ffmpeg: run it only to change them) and `smoke.sh` (a headless smoke run and `tools/launch-smoke.ps1` against it, from its read-only mount). The scripts and AppRun are committed executable (`git add --chmod=+x`). |
| `tools/write-built-in-accounts.ps1` | Writes the gitignored `src/Launcher.Core/Scraping/BuiltInAccounts.Release.g.cs` (ScreenScraper's developer credentials, scrambled) from `SCREENSCRAPER_DEV_ID` and `SCREENSCRAPER_DEV_PASSWORD`, for the release workflow (docs/ARCHITECTURE.md A5, "Secrets"). `-Remove` deletes it. Never commit that file. |
| `docs/manual-tests.md` | Checks a script can't observe (window focus with a real emulator). |
| `tools/core-bench/` | Times Core's config, scan and query paths on self-contained .NET 8 (the export's runtime). Not in the solution. |
| `tools/synthetic-library/` | Writes a portable user folder with 20 systems and 14,215 games (10,000 on PS2), with covers hardlinked from a folder of JPEGs (`<covers>/jpg/00000.jpg` to `09999.jpg`: the M1 spike library's, or 512×720 stand-ins it writes with `--generate-covers`, about 850 MB in a minute). No derivatives: the games grid decodes the images itself. `--games`, `--others`, `--slots=back,spine,...` (art for more slots) and `--models=<n>` (that many PS2 games get a per-game model) make other libraries. Not in the solution. |
| `tools/classic-view-logos.py` | Writes the Classic View theme's logos (`godot/themes/classic-view/logos/`) from Carbon's (`system_logos_all/`, then `system_logos/`): SVGs rendered with ImageMagick's librsvg, cropped, at most 512 px, WebP. Lists the built-in systems left without a logo and the mostly dark logos. Needs Pillow and `magick`. |
| `tools/bench-summary.py` | One line per bench run (scroll, textures, memory) from `artifacts/bench/<folder>`. |
| `tools/scrape-cli/` | `odyssey-scrape`: every scraping operation from the command line (`providers`, `game`, `system`, `missing`, `clear`, `show`, `resume`, `bake`, `scan`, `ss-systems`, and `launchbox-update` and `launchbox-info` for the local copy of LaunchBox's database), for live tests with the owner's credentials, the model commands (`import-model`, `remove-model`, `inspect-model`, `models-log`; no network), `import-gamelist` (an ES-DE `gamelist.xml`; no network), and the theme commands (`ThemeCommands.cs`: `inspect-theme`, the list owner's check, no network; `themes list|install|update|remove`, the downloader's work, git with no credentials). In the solution. |
| `tests/Launcher.Core.Tests/Scraping/Fixtures/` | Recorded provider responses. Credentials appear as `{{DEVPASSWORD}}`-style placeholders, which the tests' fake HTTP handler fills with fake values. |
| `godot/themes/` | The app's own themes. Godot ignores the folder (`.gdignore`: no `.import` files, nothing in the PCK); the export copies it to `themes/` beside the executable (`godot/addons/odyssey_export/`), and the app reads it from there (from `godot/themes/` in an editor run). |
| `godot/themes/memory-card/` | The base theme, not one to choose: `theme.toml` (looks, templates and each built-in system's colour and template, and the look of the first 14) and its models. Every theme builds on it: what a theme leaves out is memory-card's, and its templates are every theme's to name (docs/ARCHITECTURE.md A6). |
| `godot/themes/slab/` | Slab, the default theme (2026-10-08): a black to dark grey background and dark grey menus (`[ui.menu]`, 2026-10-15: docs/ARCHITECTURE.md A6, "Menus"), and one dark grey slab (Memory Card's generic card's shape, `models/systems/slab.glb`, from the generator) for every system, its front a `label` showing the system's image from `logos/<system id>.webp` (`[defaults.system_slots]`: docs/ARCHITECTURE.md A6, "System cards' logos"). 176 images: 174 from the owner's ES-DE set (Canvas's controller images, `_inc/carousel-icons-controller/clear` in github.com/Siddy212/canvas-es-de; `slab_images/` at the root, untracked: the ones matching a built-in id, `megacd.webp`, `megacdjp.webp` and `sfc.webp` added 2026-11-03; `favourites`, `recently_played`, `all_games` renamed (`all_games` supplied on its own, 2026-10-15), cropped to their content and at most 512 px by `tools/slab-logos.py` (about ten minutes); `psvita.webp` (2026-10-28) went through the same steps from ES-DE's own copy of the set, its linear theme's `system/systemart/psvita.webp`), plus `ps5.webp`, which ES-DE lacks: made by hand (2026-10-15) in the same layout from a PS5 controller and logo (untracked `ps5/` at the root), so `tools/slab-logos.py` deletes it unless its source gains a `ps5` image; and `dreamcastnajp.webp`, the Dreamcast's (its controller has the NA/JP orange swirl), which `tools/slab-logos.py` copies (`COPIES`). |
| `godot/themes/console/` | Console (the default until 2026-10-08): each system's console as its card, many with a `focused` clip and some playing a video (`videos/<id>.mp4`) while focused; for a system with no hardware, a device, an object or its emblem made solid. Every built-in system has its own card; everything else is memory-card's. The list of cards is in `tools/console-models/README.md`. |
| `godot/themes/classic-view/` | Classic View (2026-10-19), the look of a 2D launcher: a wallpaper (`wallpapers/main.webp`, the 1080p one from `tools/wallpaper/`), `[motion]` at 0 (no sway or bob), every game Memory Card's `flat_cover` (`[defaults] game_template`), one light straight on, and one flat 16:9 dark grey card for every system (`models/systems/classic.glb`, from the generator) with the system's logo from `logos/<system id>.webp`: 165 from Batocera's Carbon theme (`sfc.webp` its `sfc-w.svg`, 2026-11-03; `megacdjp.webp` its Japanese Mega-CD logo, `jp/megacd.svg`, found by `NAMES`), made by `tools/classic-view-logos.py` (about four minutes) from the untracked `system_logos_all/` (Carbon's whole set, by Batocera's names; a `-w` variant, drawn for a dark background, wins) and `system_logos/` (ES-DE's names, for the few the first lacks), and `dreamcastnajp.webp`, which the script derives from Carbon's Dreamcast logo, its swirl turned from PAL blue to orange (`DERIVED`). The 10 built-in systems with no logo print their names (`[systems.<id>.slots] label = ["generated"]`). |

## Commands (PowerShell, repo root)

| Command | Does |
|---|---|
| `dotnet build` | Builds the whole solution (`OdysseyLauncher.slnx`). |
| `dotnet test` | Runs the tests on Microsoft.Testing.Platform (selected in `global.json`), including the scan benchmarks (about 12 s; they run alone, after the parallel tests). |
| `.\tests\Launcher.Core.Tests\bin\Debug\net8.0\Launcher.Core.Tests.exe -trait "Category=Benchmark" -showLiveOutput` | Runs only the benchmarks and prints their timings. |
| `dotnet publish tools/core-bench -c ExportRelease -o artifacts/core-bench` then `artifacts/core-bench/core-bench.exe $PWD/artifacts/core-bench-work` | Core timings on the export's runtime. **Use this for any Core number you compare with a target** (results in `docs/perf/m2-core.md`). |
| `godot --headless --path godot --build-solutions --quit` | Godot's own C# build. Exits 1 if it fails. |
| `godot --headless --path godot --import` | Imports assets and generates the `.uid` and `.import` files. Commit those files. |
| `godot --headless --path godot --quit-after 10` | Smoke run. Prints the `Launcher.Core ...` line. |
| `.\tools\launch-smoke.ps1` | Headless `--launch` of the fake emulator; checks the exit code, arguments and working folder. `-Windowed` shows the window, `-SleepMs` sets the play time, and `-Executable artifacts/export/windows/OdysseyLauncher.exe` runs the export. Needs `dotnet build` first. |
| `.\tools\verify.ps1` | All of the above, in order. |
| `godot --path godot` | Runs the app windowed. Use `godot --path godot -e` for the editor. |
| `godot --path godot --export-release "Windows Desktop" $PWD/artifacts/export/windows/OdysseyLauncher.exe` | Exports an ExportRelease build (the preset is in `godot/export_presets.cfg`), with the themes copied to `themes/` beside it by the `odyssey_export` addon (so build the C# solution first). **Not `--headless`:** the shader baker needs a rendering device, and a headless export silently bakes nothing (a 49 KB PCK instead of about 2.6 MB). |
| `godot --path godot --export-release "Linux" $PWD/artifacts/export/linux/OdysseyLauncher.x86_64` | The Linux export (x86_64), made on Windows; not `--headless` either: the baker bakes Vulkan's SPIR-V, and the PCK is about 1.2 MB. |
| `.\tools\linux\make-appimage.ps1` | The Linux export, then in WSL (`-Distro`, `OdysseyLinux` by default) the tools, the AppImage (`artifacts/linux/`) and its checks. `-SkipExport` packs the export that's there. Run `dotnet build` first. The distro is made once with `wsl --install Ubuntu-24.04 --name OdysseyLinux --no-launch`. |
| `wsl -d OdysseyLinux -u root --exec bash tools/linux/test.sh` | The build and the tests on Linux, without the benchmarks (about 15 s after the first build); arguments go to `dotnet test`. Run `tools/linux/setup.sh` the same way first, or `make-appimage.ps1`. |
| `.\tools\bench-export.ps1` | Exports, then runs one warm-up plus 5 benched runs of the export and prints the medians. Options: `-SkipExport`, `-Runs`, `-Frames`, `-Resolution`, `-Fullscreen`, `-EngineArgs '--rendering-driver', 'vulkan'`, `-Label`, `-AppArgs "--user-dir=$PWD\artifacts\synthetic", '--bench-scenario=scroll'`, `-TimeoutSeconds`, `-Executable` (another export, to bench two builds side by side). **Use this for any number you compare with a target**, with nothing else running on the machine. |
| `godot --headless --path godot res://scenes/tools/generate_box_templates.tscn` | Regenerates memory-card's models, the test theme's and the sample theme's (deterministic). Commit the `.glb` files (none is imported). `BuiltInModelTests` and `ModelInspectorTests` check them against the model spec and budgets. |
| `dotnet run --project tools/synthetic-library -c ExportRelease -- "--out=$PWD\artifacts\synthetic" "--covers=$PWD\artifacts\covers" --generate-covers` | The synthetic library, for `--user-dir`. About 50 s, plus a minute the first time to write the covers (`--generate-covers` writes only those missing; the covers folder must be on the same volume as `--out`). M6's 3,000-game library with art for four more slots: `"--out=$PWD\artifacts\synthetic-3000" ... --games=2620 --others=20 --slots=back,spine,screenshot,logo`, then copy `tests/themes/slot-showcase` (and `samples/themes/retro-tv`) into its `themes/`. ## Debug facilities (windowed only: headless mode doesn't render)

Use these to check your own work. Look at captures with the Read tool, and compare bench JSON before and after a change.

```powershell
godot --path godot --resolution 1280x800 --fixed-fps 60 -- --capture=$PWD/artifacts/shot.png --capture-frame=60
godot --path godot --resolution 1280x800 -- --bench=$PWD/artifacts/bench.json --bench-frames=600
```

- **`--capture`** saves a PNG of the viewport after n drawn frames (`--capture-frame`, default 60), then quits.
- **`--bench`** samples n frame intervals from `interactive` (`--bench-frames`, default 600), writes JSON, then quits. The JSON (format 2) contains:
  - `app_startup_ms`: **our code's start-up**, from the first autoload's `_EnterTree` to `interactive`. The 1 s target applies to this number only. Engine and .NET start-up before it is excluded.
  - `startup_ms`: ms since the process started, with `engine_start`, `autoload_enter_tree`, `main_ready`, `first_frame_drawn` and `interactive`.
  - `frames`: mean, p50, p95, p99, max, `hitch_count` (over 1.5× the refresh interval) and the worst frames.
  - `render_ms`: render CPU and GPU times.
  - `gc`: GC activity, including `main_thread_allocated_bytes`.
  - `scenario`, `options`, `library`, `memory`, and in the scroll scenario `scroll` (the scroll frames alone, textured fraction, main-thread allocation) and `textures`.
- **`--bench-scenario=scroll`** enters the biggest system (or `--bench-system=<id>`; `all_games` for All games) and scrolls from the first row to the last in `--bench-scroll-seconds` (default 60, the M1 rate). **`--no-textures`** is the control the hitch target is compared with, in the same session.
- **`--render-scale=<0.25–1>`** and **`--upscaler=bilinear|fsr`** override the automatic cap of 1080p for 3D (FSR1 needs Forward+). **`--upload-cap=<n>`** sets the cover-sized uploads per frame (default 4, a 256² slot layer counting a quarter; 0 = no cap).
- **`--start-system=<id>`** (with **`--start-index=<n>`**) enters a system once interactive, and **`--nav-script=down,right,accept,back,...`** plays navigation commands through the controller's path, one every 30 frames, logging each (`Nav script:`). Use them with `--capture` for transitions, focus and screens. The steps `theme` (the next theme, applied without a restart) and `rescan` (every system and every media folder, from any screen: Shift+F5) exercise theme switching and media rebinding; `quick-rescan` is F5's "Rescan the library" (media folders only for systems with new games). `menu` is Menu (it opens and closes the settings; in a system's games, that system's page), `power` is View (the power menu: never `accept` a row in it but Quit app, which is last), `x` is X (in the grids, the focused system's or game's options: M7 part 2), `y` is Y (in the grids, the focused system's or game's details; in a settings list, its second action), `favourite` is L3 and `zoom` is R3 (the focused game large in the middle of the screen, and back); while a settings screen or options panel is open, the steps go to it. Unknown steps (`wait`) do nothing, for giving a save or a load time to finish. `click` (the left button on the focused control), `scroll` (the wheel, three notches) and `type` (the keys "Ok 1") send real mouse and keyboard events. `turn` holds the right stick right and a little up until the next step, turning the focused item (a joypad event from a device id of its own).
- **`--open=settings|keyboard|folder-picker|image-picker|program-picker|confirm|progress|power|match|art|details|manual|running|themes|update`** shows a settings screen or shared component once interactive (M7), with **`--open-path=<folder>`** for where a picker starts. `progress` makes a job with made-up numbers, for its card. `match` shows the manual-match panel ("scrape this game") over made-up results (with made-up covers, and one "No cover") for `--start-system`'s game at `--start-index`; nothing is searched, downloaded or scraped. `art` shows the match panel and, over it, the art chooser (a SteamGridDB game's covers, logos and heroes, one step per kind) with made-up images and a current cover to keep; its last pick is only logged (`Art:`). `details` shows that game's details screen (as Y does); `--nav-script=accept` then plays its video full screen (the first card, when it has one). `manual` opens that game's manual (as A on its card does: `--nav-script=right,accept,down` turns a page, zooms and scrolls); the game needs a manual in its media folder. `running` shows the black "Running <title>" screen a launch shows, for a made-up game; nothing is launched. `themes` opens the theme downloader (Settings, Appearance, Download themes), which fetches the published list unless **`--themes-list=<folder>`** names a local one (`tests/themes-list` for captures: nothing is fetched); `--nav-script=x` then opens the first theme's details. `update` presses Settings, About's "Check for updates", which asks GitHub unless **`--update-feed=<folder>`** names a local feed (a `releases.json` in GitHub's shape and the packages it names by relative URL: nothing is fetched); in an export, `--nav-script=wait,wait,accept` then downloads the update, installs it and restarts (with the same arguments, so the restarted launcher checks again). An editor run never installs. **Don't run an update from GitHub yourself:** it replaces the export it runs from; use a local feed in `artifacts/`. Captures that save settings should use a copy of a library's config (`--user-dir`), not a bench library.
- **`--layout=<systems>[:<C>x<R>]/<games>[:<C>x<R>]`** uses those layouts instead of settings.toml's `[display]` ones: the systems `grid`, `grid_with_labels`, `carousel`, `single` or `coverflow`; the games `grid`, `grid_with_labels`, `carousel`, `list`, `coverflow` or `showcase`; a grid with columns and rows (0 automatic), e.g. `--layout=grid:4x2/list`. A system's own `games_layout`, `games_columns` and `games_rows` still win. The bench report records the layouts (`options.layout`).
- **`--theme=<id>`** uses that theme instead of settings.toml's `[display] theme` (a user theme must be in the user folder's `themes/`; a user theme with a built-in theme's id replaces it, so check a user folder's `themes/` when a built-in theme looks wrong). `--theme=memory-card` runs the base theme alone, which settings.toml can't choose. **`--no-overlay`** hides the text overlay (and the status indicators, and the grid with labels' labels), whose scrims darken the screen's top and bottom, so a capture shows a look's corners (exact on Forward+, within 2/255 on Mobile: ARCHITECTURE.md A6).
- **`--button-icons=xbox|playstation|nintendo|gamecube|steamdeck|steamcontroller|keyboard`** makes the controls' hints show that kind's buttons for the run, whatever is pressed and whatever `[ui] button_icons` says. Without it, a nav script's steps count as keyboard presses, so the hints show the keyboard's keys.
- **`--ui-size=small|medium|large`** uses that UI size for the run instead of `[ui] size` (docs/ARCHITECTURE.md A1, "UI size"): for captures of how each screen fits.
- **`--fake-status=<battery>/<network>`** makes the status indicators (top right) show a made-up state instead of the device's: the battery `none`, a percentage, or a percentage and `+` (plugged in); the network `off`, `lan` or `wifi0`–`wifi3` (its bars). For example, `--fake-status=8/wifi1`.
- **Animations: Godot's movie mode.** `godot --path godot --resolution 1280x800 --fixed-fps 60 --write-movie <folder>/f.png -- --boot-frames=90 --nav-script=...` writes every frame as a PNG (`f00000000.png` on), at about a fifth of real time; a movie's frame n is the one the log calls frame n (`Nav script: ... (frame n)`), and `--capture` ends the run. **`--boot-frames=<n>`** holds the scene back until drawn frame n, so a movie is the same frame for frame on every run: otherwise boot lasts as many frames as its background work takes time, and the items' idle bob (the shader's `TIME`) counts from the engine's start. Only art streamed in on worker threads (covers as a grid appears, models in a theme switch) can still arrive a frame apart. `tools/made-up-games/readme_captures.py` makes the README's animations this way. Not for benches (it holds the start-up marks back).
- **`--memory-log=<path.csv>`** appends the app's memory once a second (Godot's video, texture and buffer memory, working set, private bytes, managed heap) with what it's doing (`browsing`, `running` while a game runs, `returned`), until it quits. `tools/gpu-memory-run.ps1` runs an export with it while sampling Windows' GPU memory counters for the process, and `tools/gpu-memory-summary.py` gives per-phase medians (docs/perf/spike-direct-images.md). Not for frame-time runs.
- **`--save-responses`** saves each scraping provider's response (credentials redacted) in `DataDir/scraped/responses/` for that run, to debug a scrape. Off by default. `odyssey-scrape` takes it too.
- **`--launch=<system>/<rel path>`** launches that game once the app is interactive, scanning the system first if the game isn't in the library. It works headless too.
  - **`--user-dir=<folder>`** keeps config, data and cache in that folder (the portable layout), instead of AppData.
  - **`--quit-after-launch`** quits once the game has ended: exit code 0 if it ran, 1 if the launch failed.
  - The log lines start with `Launch`, including the exact command line, when the emulator took the foreground, and how the launcher got it back.
  - **Don't run a windowed `--launch` of a real emulator yourself:** it hands the foreground to the emulator and takes it back from the owner's desktop (possibly with a synthetic Alt key). That's the owner's manual test.
- User arguments go after `--`. Use `++` instead if a shell swallows `--`.
- **Paths must be absolute.** With `--path`, Godot changes the working directory into `godot/`, and a PNG saved there would be imported as an asset. `artifacts/` is gitignored.
- Use `--fixed-fps 60` for captures, so animation is deterministic. **Never** use it with `--bench`.
- Don't combine `--capture` with `--bench` for measurements, because the PNG write shows up as one long frame.
- Exit codes: 0 means success; 1 means a failure, including a headless run or a watchdog timeout (30 s plus 100 ms per requested frame); 2 means invalid debug arguments.
- Timings from the editor binary with Debug assemblies aren't comparable with the performance targets. Use `tools/bench-export.ps1` for those.
- Libraries for runs: `--user-dir=$PWD/artifacts/synthetic` (see above), or a user folder whose `systems.toml` points `rom_dirs` at the owner's NAS (`S:\`, read only; see docs/perf/m5-navigation.md). The app scans systems never scanned in the background, except in benches.
- `DebugHooks` must stay the **first autoload**, because `app_startup_ms` is timed from its `_EnterTree`. It warns if it isn't first.

## Decided stack (don't change without asking)

- Godot 4 .NET edition with C#. Use Godot 4 C# APIs only, and check their signatures against https://docs.godotengine.org/en/stable/. Godot 3 examples are wrong: for example `Spatial` is now `Node3D`, `yield` is now `await ToSignal(...)`, and string-based `Connect` is now C# events or `Callable`.
- Target frameworks follow what Godot generates, which is net8.0 for 4.7.2. Bump every project together.
- TOML via Tomlyn. Config files are the source of truth for user intent.
- SQLite via Microsoft.Data.Sqlite, in WAL mode, with versioned migrations. `library.db` must be rebuildable from config, disk and scrapers. User data that can't be rebuilt goes in `userdata.db`.
- Media lives on disk, and the DB stores relative paths only.
- 3D models are glTF 2.0 `.glb` only.
- Platform-specific code (paths, processes, window focus) lives only in `src/Launcher.Core/Platform`, behind interfaces.

## Rules

- **Ask before adding any NuGet package**, including test and analyser packages.
- **Never commit credentials.** API keys and passwords live only in the user's `secrets.toml` or in `ODYSSEY_*` environment variables, and ScreenScraper's developer credentials also in the repository's GitHub secrets, from which the release workflow builds them in. Never put them in the repo, tests, logs or bench output.
- Launcher.Core must never reference Godot. `ArchitectureTests` enforces this.
- The Godot main thread must never do file, network or DB I/O, never decode images, and never call `.Wait()` or `.Result`. Never touch the scene tree from another thread. Work on another thread that calls into Godot at all (an `Image`, a `GltfDocument`, a texture) goes through `GodotWork.TryEnter`/`Exit` (a long-lived thread also stops on `GodotWork.Quitting`), so quitting waits for it: otherwise a quit can crash in the interop.
- No allocations in per-frame code (`_Process`, grid updates, `frame_post_draw` handlers). That means no LINQ, closures, boxing, string formatting, or implicit `string`→`StringName` conversions. Cache every `StringName` and `NodePath`.
- For a performance-sensitive change, run `--bench` before and after, and quote both results.
- For a visual change, run `--capture` and look at the PNG.

## Conventions

- Godot script classes are `partial`, and each file is named after its class (Godot requires this).
- The Godot project has no ImplicitUsings, because `Godot.Environment` clashes with `System.Environment`.
- In Core, every `await` uses `ConfigureAwait(false)`. CA2007 is an error in `src/`.
- Warnings are errors in Core and in the tests.
- File-scoped namespaces. Core namespaces mirror its folders (`Launcher.Core.Diagnostics`, ...).
- A schema change means a new numbered migration file. Never edit a shipped migration.
- Tests never touch the network. Scraper tests use recorded fixtures through `FakeHttpHandler`, which fails a test on any request it has no route for. Waits go through the injected `Delay`, which advances a test clock instead of sleeping.
- `Redactor` masks credentials before anything is logged or saved. Provider code must never put a URL or header into a message unredacted.
- Use UK English in docs, comments, UI text, our own identifiers and our config keys (`favourite`, `colour`). External names keep their own spelling (Godot `Color`, glTF `baseColorTexture`).
- Don't rewrite source files with Windows PowerShell's `Get-Content`/`Set-Content`: it reads UTF-8 without a BOM as ANSI and mangles non-ASCII characters. Use the editor tools, or Python with `encoding='utf-8'` and LF line endings.

## Code-writing guide

These keep the code maintainable for human developers. Code already in the repo doesn't meet all of them yet: don't make it worse.

- Keep functions small and flat: at most 3 levels of nesting, early returns, one job each.
- Add a function or method only when it's called from 2+ places, the request asks for one, or it's needed for an interface, an override, an event handler, per-frame code (instead of a closure) or the complexity limit. No pass-through wrappers outside `src/Launcher.Core/Platform`.
- Code only for the cases the request names or the existing code already handles. Input from outside the app (config, ROM folders, scraper responses, models, downloaded themes) always fails safely, as the surrounding code does. For any other risk you see, list it in your reply and ask; don't code it.
- Comment only the why (a decision, a constraint, a link to docs/ARCHITECTURE.md). Update or delete a comment when its code changes. No commented-out code.
- Keep cyclomatic complexity at 20 or less per function. Nothing checks it yet (CA1502 for C# and ruff's C901 for Python will, after a clean-up of the code already over it), so count it yourself. If a function goes over, simplify the logic first; split it only if that isn't enough. A function that has to stay over (a mapping `switch`, say) gets a comment saying why.
- Don't let a file grow past 1,500 lines, and don't make one already past it longer: propose a split instead.
- Search before writing: reuse the existing kits and helpers (`card.py`, `handheld.py`, `screens_print.py`, `Redactor`, `GodotWork`) instead of near-copies.
- No speculative generality: no single-implementation interfaces outside `Platform`, no options or parameters nobody asked for.
- Keep a change to its request: clean-ups go in their own commit.
- New Core behaviour comes with a test; a bug fix with a test that fails without it.
- Never swallow an exception silently: log it through `Redactor`, or let it propagate.
